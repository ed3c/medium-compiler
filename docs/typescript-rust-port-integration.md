## Transferable engineering method (not Rust-for-Rust's-sake)

1. **Preserve the canonical semantic Owner.** A faithful port follows the original compiler's documented algorithms, file/function decomposition and diagnostic semantics. PORTING.md maps original Go packages/functions to Rust modules and preserves operation order. A visual/architecture analogy must retain its own original Source/Owner; no newly inferred graph edge becomes a true Native handoff.
2. **Code-intel / structural mapping, not name-based reconstruction.** Record canonical revision, language/parser, selected source symbols, actual producers/consumers and reachable dependencies; log dynamic/unknown edges. For syntax changes, use existing AST/codemod migration tools. Port only selected behavior, and preserve original modules otherwise. A generic syntax tree does not prove call-graph or semantic equivalence.
3. **Upstream watch and conformance are distinct.** Vinext's daily upstream-diff triage and nightly Next.js compatibility matrix demonstrate `Upstream change -> affected Consumer -> focused reproduction -> selected original tests -> correction -> new comparison`. Adapt this *procedure* only when a real maintained fork/port exists. It does **not** justify adding an always-on cron or cross-repository scan to medium-compiler.
4. **Original reference and treatment must be version matched.** tsrs has a TypeScript 7.x target, but medium-compiler runs TypeScript 5.9. Do not run `tsrs --noEmit` next to existing `tsc --noEmit` and label any difference a migration bug. For a future isolated 7.x research experiment, first pin both `tsgo` and `tsrs` to **the same upstream TypeScript commit**, same compiler options, source files, dependency graph, worker count, OS/CPU and environment. Neither is currently installed or tested by this project.
5. **Compare Consumer-observable contracts, not just "errors appeared".** Capture the *original* diagnostic code, file, start, length, message, severity, order and exit status, plus selected JavaScript/.d.ts/.map outputs and effects when emit is in scope. Preserve raw order by default. tsrs documents some known diagnostic-order discrepancies: do not silently sort away these failures. Normalize only an explicitly original-Owner-approved non-deterministic field. Include positive, legitimate neighbor, wrong-version, missing file, changed-order and changed-code planted controls. Distinguish `FAIL`, `INCONCLUSIVE`, `NOT_RUN` and unsupported flags.
6. **Benchmark only after parity for the *actual* Consumer.** Use equal worker/thread and memory constraints; record wall time, peak RSS, native vs WASM, cold/warm and resource limits. Cloudflare's "up to 8x faster / approximately 70% less memory" is an early upstream comparison to TypeScript **7.0**, not an outcome for TypeScript 5.9, our project, Cloudflare Workers or browser Typed Code Explorer.

## Typed Code Explorer and Rust/Wasm boundary

The user-selected **VIS-08 A Typed Code Explorer** still needs real compiler/schema-linked Type and Symbol readback, not guessed strings. An *experimental* tsrs checker and `@tsrs/wasm` could later supply a bounded TypeScript 7.x diagnostic/emit capability; the WASM distribution targets **WASI Preview 1** and is **single-threaded**. Its current browser playground explicitly does **not** guarantee full hover/type inspection, automatic type acquisition or production LSP parity. Do not use a `tsrs` CLI binary as a substitute for a browser JS/TS compiler API.

For this workstream, prefer **read the original TypeScript 5.9 AST and typechecker already used by medium-compiler**. Add tsrs only in a separately scoped opt-in proof if there is a named source-verified gap or measurable advantage. No product dependency, Cloudflare worker upload, sandbox relaxation or production package/version upgrade is selected here.
