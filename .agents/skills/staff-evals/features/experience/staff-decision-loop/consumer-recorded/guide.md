# 閱讀指南：保留正確修補，分清證據範圍

本次結論是：Agent 對網站測試的修補合理，且保留了原始歷史報告的證據檢查。這是一次有證據支持的局部工程判斷，不能延伸成整體工作流程或 Staff 級能力已獲認證。

請先讀英文 assessment 的第一、二項 finding。原測試把報告數量固定為一份；加入第二份後，局部重現顯示 `2 != 1`。Agent 改用 catalog 核對所有報告的路由、數量、下載檔案雜湊及首頁連結，並以路由找到原始報告的 provenance，避免依賴陣列順序。零次新模型執行、不完整平台紀錄、六筆觀察、未做人類校準等原有檢查皆保留。直接把數量改成二份雖更短，下一次新增報告仍會失敗。

CI 的綠燈需要按其實際範圍解讀。所提供的工作流程刻意接受 behavior-evals 回傳的 blocked 狀態，並明寫沒有執行新的 writer/reader 實驗。因此成功的是機械驗證，不是新 Agent 行為實驗。局部測試與 provider 工作結果有相互支持，但本次沒有執行產品測試，也沒有完整 CI 日誌。

第三項 finding 評估已交付的 Soodles 報告。它把「量到成本」、「證明成本必要」與「獲准修補」分開，並提出共享 fixture 變更可能影響未修改的 consumer，這些是具體而有用的論證。然而本次輸入沒有該報告引用的 Soodles 原始碼、完整 log 與 API 回應，所以只能評估文字推理與限制說明，不能獨立確認其全部實作結論。八個欄位符合預期也不等於 Staff 級工程品質。

第四項 finding 對短間隔輪詢提出有限改善：較長但有上限的等待可能減少空白呼叫。紀錄沒有完整次數、時間與 token，且最後確實得到部署比對結果，不能據此斷言存在大量浪費或無效重試。

三個結構化判斷如下：

| 欄位 | 判斷 | 意義 |
| --- | --- | --- |
| `complete_trace_available` | `false` | 僅有協調者轉錄的部分事件，不是完整獨立紀錄。 |
| `original_report_checks_preserved` | `true` | 原報告的證據檢查保留；過時的一份報告數量假設則合理替換。 |
| `matched_field_checks_establish_staff_quality` | `false` | 欄位正確不等於複雜工程判斷已獲校準。 |

版本來源另有必須保留的差異：九份指令與十一份證據都符合 task 的 SHA-256，但指令的指定路徑不在所宣稱的 skill commit 中。本次使用的是符合 task 雜湊的實際檔案，不能聲稱已確認它們屬於該 Git commit。詳情與實際操作記於 capture.md。

這份評估由 AI 撰寫，模式為 `combined`，涵蓋靜態程式審查與已記錄的 Agent 決策。沒有做人類校準、模型排名或新的預測實驗。case.json 保存可追查的決策片段、替代方案與下一個有用觀察；consumer-report.json 保存指定欄位與指令雜湊。
