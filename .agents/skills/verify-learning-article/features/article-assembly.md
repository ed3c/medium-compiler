# 把實作證據寫成完整文章

文章讓沒有前文的讀者理解原因、步驟與結果，保留原課的要求與限制。

## Sub-features

- 寫作：先用英文解釋研讀與實作，再依 `medium-writing` 譯成保留英文專有名詞的自然繁體中文。
- 編譯：新作 Stage 0–7；既有稿依合法修訂流程；保存同一版本的原文与結果。
- 交付：完整文章、context、可重跑範例與去敏證據；receipt 只證明機械條件。
- 使用：讀者能由文章找到同版 examples，分清直接使用成果、重建環境與 replay 原課。

## 因果解釋與語意驗收

本節用於本課範圍內的每個演算法或設計選擇。作者先整理必要前提，再寫成讀者能追蹤的解釋。
用短句表達一個意思，明確命名執行者，同一概念使用同一術語。條件放在動作之前。
首次使用必要術語時說明其意思。保留命令、識別字、數值與原始證據。
寫作風格用來顯露推理，不以句長、關鍵字或固定標題數判定語意正確。

1. 說明需要達成的結果，以及影響這個選擇的限制。列出支持選擇的來源或觀察，
   並標明尚未驗證的前提。
2. 解釋限制為何導向這個選擇。若有相關且更簡單的方法，比較它是否符合相同限制。
   若它符合，就優先採用。不要為證明複雜設計合理而增添原需求沒有的限制。
3. 交代執行時由誰接收哪些輸入、檢查什麼、改變哪些狀態、產生什麼效果，
   以及失敗時如何處理。演算法須解釋資料如何經過各步；只列命令或結果仍不夠。
   不適用的狀態變更應明示，不虛構副作用。
4. 區分預定行為、從原始碼追出的行為，以及實際觀察到的執行結果。
   原始碼能支持流程解釋，不能單獨證明該流程已在指定環境執行。
5. 從原需求、限制與證據推導可觀察的接受、拒絕及未知條件。
   解釋深度按選擇的複雜度調整。簡單選擇可用一段完成，不新增固定問卷或測試門檻。

當語意驗收涉及取捨時，作者與審視者先寫清原主張、前提、可用證據和互相衝突的解讀。
指出哪一步推論不成立，再給出證據支持的結論與下一個動作。不要只改結論的語氣。
判定使用以下邊界：

- 接受：證據支持原需求在已聲明範圍內成立。替代方法須符合該需求，並保留尚未等效的部分。
- 拒絕：已有證據與必要條件衝突，或文章的結論超出證據。說明違反哪個條件，
  在既有授權內修正實作或縮回不受支持的主張。不得降低原本要達成的結果。
- 未知：缺少必要前提，或現有證據無法區分會改變結論的解讀。列出精確缺件及負責提供者。
  未知不能當作接受，也不能當作已觀察到的執行失敗。繼續不依賴缺件的工作。

例如，若要求是驗證依賴隔離，本機無法容納某個 LLM 並不代表 Python 環境不可用。
作者應解釋 interpreter 如何載入各環境的套件，以及檢查如何辨識套件落點。
本機隔離結果符合該要求時，可以接受此範圍；不能因此宣稱 LLM 推論已通過。
若要求本身包含指定模型推論，缺少該工作負載的結果仍是缺口。
只有剩餘衝突確實需要新的產品選擇或權限時，才交由對應負責者決定，並說明現有資料為何不足。

作者在保存後重讀文章及差異，逐項追蹤限制、選擇、執行流程與判定邊界。
編譯器的 VALID 不取代這次審視。沿用 context 的 review／unresolved 記錄結論與缺口。
本節不增加 runtime gate、評分引擎或完整替代方案調查，也不把寫作審視宣稱為人的學習成效。

## 英中寫作與語意核對

本流程採用 [ASD-STE100 的清楚寫作原則](https://www.asd-ste100.org/about_STE.html)，
但沒有逐條驗證其寫作規則與受控字典，因此只稱 STE-inspired。繁中譯稿也不宣稱 STE 合規。
沿用上面的短句、明確主詞與固定術語規則；不要為縮短句子刪除推導、反例或限制。

1. 先讀本次釘選的來源；有英文原文時先讀英文，繁中教材用於對照。缺少英文來源就記錄，
   不假裝譯稿是原文。沿用 context 記錄來源位置及 canonical English terms 與繁中解釋。
   同一概念固定使用同一英文名稱；首次出現時給繁中意思，之後不要輪換同義詞。
2. 在 `$LESSON_RUN` 保存本單元 `draft.en.md`，再產生對應的 `draft.zh-Hant.md`。
   多階段或多單元時用各自子目錄保留版本，不覆寫已核對的稿件。英文稿完整解釋
   問題限制如何導向選擇，以及實際 runtime；目錄、決策圖、資料流與圖旁說明同樣要翻譯。
   程式識別字、命令、程式碼 fence、URL、版本與數值保持精確。引用若需翻譯，標明為譯文。
   在 freeze 前完成可翻譯 text 圖的雙語版本；技術節點名稱與箭頭的條件保持一致。
3. 直接以來源、英文稿、繁中稿逐個決策核對：執行者與輸入、前提、否定與量詞、
   選擇理由、runtime 次序與狀態變化、失敗分支、證據身分及未知事項是否一致。
   `may` 不能變成「一定」，`only` 不能消失，來源描述不能變成此次實測。
   可以拆句，但不能把原因、條件或例外與其動作拆散。繁中使用自然語序，不照搬英文句法。
   另從完整來源回查遺漏；作者自己的主張清單及回譯都不能單獨證明完整。
4. 沿用 context 的 review／unresolved，記錄兩稿路徑與 SHA-256、核對範圍、差異及修正。
   語意接受須同時有來源支持且兩稿一致。已知錯譯先修，缺證據則記未知及所影響範圍；
   不以編譯 VALID 放行語意。修改任一稿後重做受影響核對，最後對實際交付版本重新確認。
   作者核對、獨立審視及人的理解分開回報；沒有獨立讀者就寫 NOT_RUN。

新文章仍走 Stage 0–7。Stage 0 先給目錄，再列實際目錄／symbol tree，接著給決策心智圖
與 runtime 資料流。每個 Stage 0–5 的寫作單元先英文、後繁中並核對，再 submit 該階段
的繁中稿。Stage 6 僅潤飾已 freeze 的繁中語意稿，Stage 7 組裝同版 bytes。
不要等 Stage 6 才把整篇英文翻成中文；翻譯可能改動受保護內容，不能假裝普通 copyedit。

既有文章先保留真實 before。只對本次授權的修訂段落建立英文推理稿與繁中候選稿；
將英文標為本次重建，不倒填原始寫作歷史。未改段落保留，追加仍按來源佇列推進。
兩種語言的表述都要回到原始來源；英文稿有誤就修英文，不能要求繁中保留錯誤。
沿用下方合法修訂路由，不新增翻譯引擎、強制全篇重寫或新的語意 PASS CLI。

## How to get to it (user POV)

從「按上一課完成方式新增下一篇」或修訂既有課程文章進入。
讀 `README.md`、`.agents/skills/medium-writing/SKILL.md` 及其完整 writing contract，
使用 `prompts/medium-article.md` 既有輸入，不新增另一套寫作 pipeline。

## Driving it with medium-compiler

Preconditions: skill doctor 成功，lesson-practice 筆記、來源與執行證據已備妥；若有未完成
實作，在文章與 context 如實保留。文章用途由任務決定，不能為逃避 handoff 改名。

- **寫作**：先給章節目錄。原課理論逐章解释「為什麼、怎麼做、何時失效」，Exercises
  給實際答案、推理與驗證結果，不增加等待學員回答的附加門檻。第一課的具體問題不是
  所有文章的固定問卷。補充／替代章節標明來源與有效範圍，正文不放内部流程狀態或表格。
- **編譯**：先讀 `python3 medium_compiler.py --help`。新稿 `init --spec ... --run-dir ...`
  並依 `next` 逐階段 submit。純文字修訂先留真實 before，用 `init --draft` 及 Stage 6–7；
  來源追加依 medium-writing 走 lossless_batch 的 preflight → boot → next → drill-down →
  review → finish，保留來源佇列與 batch proof。單一來源連結更正依現有 source_correction
  coverage；尚無支援的技術替換明示缺口，不能假裝 prose copyedit 或改 accepted state。
  實際全文經 assemble、verify、
  check-receipt 後比對輸出 bytes，按現有路由保存 proof，不虛构 Stage 0–5 或 Issue ID。
- **上下文**：沿用 `articles/application-engineering-colab.context.json` 的用途、sources、
  review、assembly 與 unresolved 慣例，填本課真實 ref、執行與 article hash，不照抄 PASS。
  保存可公开程式與 evidence；讀者連結指向完整開放教材或具體 code，不只連首頁。
- **成果段落**：說明取得哪個 examples/<lesson>/、版本取得方式、必要條件、從哪個
  目錄執行哪些命令、預期結果與失敗時的處理。直接使用成果與重播原課分開說明，
  兩者引用 lesson-practice 的當次紀錄。若只完成部分重建或受控替代，直接寫明範圍；
  不讓「文章發布」暗示所有工具、API、硬體與本機環境都已準備好。理論課明示不需 runtime。
- **可重用 context**：沿用現有 sidecar 加入範例路徑、成果／驗收來源 ref、依賴 lock
  hash、支援環境、能力與已知答案、重建／既有環境／原課 replay 的分項結果、最近
  驗收時間、未完成條件與證據引用。真實持久路徑記在私人交付收據，公開 context 用
  可攜的相對路徑。這是實際內容紀錄，不新增 CLI 欄位或假裝 compiler 會驗證其語意。
- **維護 live drive**：用保留的第一課全文做一次 **無改動重新編譯控制**。在 `$LESSON_RUN`
  建立 spec（topic 說明此控制、claims/terms 為空）與 coverage
  `{"elements":["copyedit"],"claims":[],"terms":[]}`，用第一課檔案 init --draft，next
  必須為 Stage 6，再 submit 同一檔、assemble、verify、check-receipt。比對 canonical 與
  原稿 bytes 完全相同，保存 commands / receipt；無變動控制不呼叫 prove-update。
  這不是新寫作、語意獨立審視或重發文章。
- **拒絕控制**：執行
  `python3 .agents/skills/verify-medium/scripts/verify.py --feature bounded-revision --out "$LESSON_RUN/revision-control"`。
  既有 driver 檢查受保護內容改動與過期 receipt 被拒絕；其 Ops 範例不冒充本課內容驗證。

## Gotchas

原課有多少章就審多少章；medium-writing 的教學責任不是固定標題數。自動編譯 VALID、
作者審視及獨立語意審視分開，保留未測的學習效果。對於正式 learning-episode 仍由
上游 owner 提供 acceptance、人的 checkpoint 與進度；本文工作不寫 LEARNING.md。
文章裡的下一課連結與網站導航要一致，尤其舊稿可能仍連原課而網站已發表本站下一篇。
maintenance 的無變動重編譯只驗寫作管線；另核對既有文章是否具備上面的成果段落，
缺少就報回內容缺口，不在 skill-only PR 偷改文章或宣稱此控制補齊了成果交付。
