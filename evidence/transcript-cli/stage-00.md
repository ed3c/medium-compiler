# 文章目錄與範圍

1. 相同的 Agent 元件，為什麼不代表相同的產品？
2. 從一項商品頁修改，看見真正的交付差異。
3. 何時值得加入驗證，何時只增加成本？
4. 把交付承諾縮成一個可檢查的契約。
5. 用結果衡量產品，再回到架構。

目的為 source-explanation。來源範圍是使用者提供的引文，以及 PodScripts 14:05、14:46、14:58、15:18 區段中對應的 Agent primitives 類比；15:18 區段後半已轉入企業議題，不把整段視為同一人的發言。原始音訊未核對，不宣稱完整改寫整集。

決策一：應由功能列表判斷產品相同嗎？比較共同元件與實際交付結果，條件是使用者是否仍需補做工作。來源是 14:58–15:18 的類比；成果量測為作者延伸。

決策二：何時重做檢查？比較盲目全跑與按依賴失效，條件是成果版本或驗收條件改變。屬作者提出的假設工作室案例，不是受訪者的實作。

決策三：是否建立自己的交付層？比較直接通用 Agent 與增加明確驗收，條件是省下的人工與返工是否超過維護成本。屬作者工程分析，尚無效益實測。

決策關係：共同元件只能說明能力集合；驗收条件定義一件工作；版本決定證據適用性；總成本決定是否值得增加工程。

主題的擬議資料結構是 request（需求版本與驗收條件）、candidate（待交付成果版本）、evidence（檢查與適用版本）、delivery（待查核或可交接）。這是文章中的設計草圖，不是已部署的 Agent 系統。

Runtime map：商品頁需求 v1 → Agent 產生候選 A → 手機版檢查通過 → 候選改成 B → 舊證據與 B 不匹配 → 重查受影響條件 → 同版本證據足夠才交接；缺失資訊時保持待查核。

寫作 runtime 另由 scripts/transcript.py 保存來源、medium-writing 撰文、medium_compiler.py 執行 Stage 0–7 admission 與組裝、scripts/build_site.py 建置文章。CLI byte checks 不證明文章語意，也不證明假設案例的效益。
