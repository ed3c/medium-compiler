# 每個人都在做 Agent，為什麼產品仍然可以不同？

把幾個 AI 產品的功能頁放在一起，很容易看見相似的清單：Agent loop、通知、第三方 connectors、context management、memory、sandbox、網路搜尋，最後再加上一個持續在線的助手。元件越來越像，產品是否也正在失去差異？

在 OpenRouter 的 Alex Atallah 與 Replit 的 Amjad Masad 參與的訪談中，有一個很好的類比：如果回到 2005 年，用資料庫、使用者資料表、登入、註冊、個人資料與登出頁面來描述網站，也會覺得大家都在做同樣的東西。但這些共同需求，沒有消除網站之間的產品差異。Agent 的共同元件，也可以理解成新的基本門檻。

這段討論可從[影片約 14:05 處](https://www.youtube.com/watch?v=ekK8urKHPMQ&t=845s)回看。這裡以其類比作為起點；以下的商品頁案例、驗證契約與成本推導，是作者為了說明工程決策提出的分析，不是受訪者展示的系統。

## 功能清單回答「能做什麼」，交付條件回答「做成了什麼」

基本門檻的意思，是使用者可能已經期待產品具備某種能力。它不表示實作很容易，也不表示所有供應商都能提供相同品質。

兩個產品都能連 GitHub，仍可能在不同地方停止。第一個產品產生 PR，工程師負責理解改動、核對需求、處理測試失敗與準備交接。第二個產品也產生 PR，但能把這些工作中的一部分接著完成。使用者看見的差異，是自己還需要投入多少判斷與操作。

要比較它們，必須先把「完成」定義清楚。如果任務只是探索一種寫法，候選程式碼就可能足夠；如果任務是交給客戶驗收，還需要特定版本的成果、相應的檢查結果，以及客戶能打開的預覽。

因此，一個可用的比較單位是「一件符合約定驗收條件的工作」。共同元件只能描述能力集合，尚未告訴我們這個單位能否穩定產生。

這也說明為什麼資料的表示方式會影響產品。若系統只記住一句「剛才測試通過」，之後很難判斷那句話適用哪個版本。若把需求、候選成果與證據分開記錄，就能問出更精確的問題：這份證據，現在還能支持這份成果嗎？

## 用一項商品頁修改，看見交付差異

假設一家小型工作室收到委託：商品頁在手機上需要固定的「加入購物車」按鈕，支援繁體中文與英文，不能遮住規格選單，而且先提供預覽。這是假設案例，沒有宣稱某個 Agent 已經完成這筆委託。

需求進來時，工作室先保存版本 v1。Agent 根據 v1 產生候選 A，檢查手機畫面與按鈕互動，留下對應 A 的結果。此時，成果與證據都指向同一個版本。

接著，客戶覺得英文按鈕太長，Agent 調整了間距與字體，產生候選 B。即使 A 的檢查全部通過，也不能直接把通過狀態套到 B。被改動的樣式可能再次遮住規格選單，或讓按鈕超出畫面。問題出在證據的適用範圍已經改變。

這時系統至少需要保存四類資料：

- **Request**：需求版本、允許的操作，以及驗收條件。
- **Candidate**：目前待交付成果的版本與預覽位置。
- **Evidence**：檢查項目、結果，以及實際檢查的成果版本。
- **Delivery**：根據現有證據，哪些條件已可交接，哪些仍待查核。

這是擬議的資料結構；四個名稱表示不同責任，不要求四個資料庫或四個 Agent。小型工具可以先用同一份 JSON 表達。真正需要的，是避免將候選成果與證據版本混在一起。

從 A 改成 B 後，系統先比對版本與受影響條件。如果能可靠地知道只改了按鈕文字和樣式，就重查相關的語系、版面與互動；如果無法判斷影響範圍，就擴大檢查或保留待查核狀態。缺少證據時，不能用模型的自信補上通過結果。

這種產品仍然可以使用與其他產品相同的 connectors、memory 和 sandbox。它的具體差異，在於版本改變時，會撤回哪些舊判斷、補做哪些操作，最後讓誰接手剩餘工作。

## 驗證值得多少成本，要放回同一件工作比較

建立上述流程需要時間。每次都執行所有檢查，也可能讓一個簡單修改變成昂貴工作。增加功能之前，應該先比較兩條可以實際使用的路徑。

**直接使用通用 Agent，再由人驗收。** 對低頻、容易看懂、出錯後能快速復原的任務，這可能已經足夠。工程師保留全局理解，工具也比較少。代價是每次都要重新確認成果與限制。

**把反覆發生的驗收問題固化到產品。** 如果使用者經常漏查語系、混淆預覽版本，或誤用先前的通過結果，可以增加版本綁定與必要檢查。代價是維護資料結構、判斷檢查失效，以及處理無法自動判定的情況。

選擇條件不是 Agent 的數量，而是第二條路徑省下的人工與返工，能否超過新增的執行和維護成本。沒有真實重複問題之前，先建立完整的協調平台，可能只是把未知成本提前引進來。

成本可以從一次完整的工作期間計算。設這段期間總共嘗試 N 件工作，其中 A 件最後通過約定驗收；所有嘗試消耗的推理費、工具費、驗證費、人工時間成本與返工成本合計為 C。當 A 大於零時，每件通過驗收的工作成本就是 C / A。失敗嘗試的費用也留在 C 裡，否則會高估效率。

這裡沒有假設任何實測數字。要比較兩種方案，還需要使用相近的任務組成與相同驗收標準，另外觀察耗時、人工介入與交付後才發現的錯誤。若 A 為零，就沒有可報告的成功交付單位成本；也不能透過降低驗收標準，製造成本下降的假象。

對商品頁案例而言，一次視覺檢查是否值得重跑，取決於它能排除的具體風險。可靠的依賴關係可以減少不必要的檢查；未知的影響範圍則需要額外觀察。省略測試本身，不構成效率改善的證據。

## 把交付承諾縮成一個可檢查的契約

如果要替這家工作室實作第一版，不需要先建立完整的 Agent 平台。可以從一個很小的交接記錄開始：目前需求版本、候選版本、每項必要檢查對應的版本、檢查結果，以及待解決問題。

交接時執行的順序也很明確。先讀取目前需求與候選成果，再確認必要檢查是否存在、是否適用目前版本、結果是否通過，最後呈現尚未解決的缺口。若需求或候選版本在檢查途中改變，就回到版本核對，不能沿用剛才的結論。

這個契約的核心性質是：被交接的成果，必須與支撐交接結論的證據相符。版本識別可以排除「檢查 A、交付 B」這種錯配，卻無法證明檢查本身設計正確。即使雜湊全部相同，仍可能缺少真正重要的驗收條件。

還有一個責任邊界：通過檢查只代表滿足已定義的檢查範圍。假設客戶只授權預覽，產品就應交付預覽，正式發布仍需要對應授權。測試結果不會自行擴張允許操作的範圍。

可以用兩個反例確認機制是否抓住問題。第一個反例把候選換成 B，保留 A 的檢查結果；系統應要求更新證據。第二個反例讓所有版本相同，卻拿掉「不能遮住規格選單」的檢查；系統應指出必要條件未被覆蓋。前者檢查版本一致，後者檢查需求覆蓋，兩者不可互相替代。

## 資料要能改變下一次工作，才開始累積價值

保存 traces 是起點。下一步需要辨識失敗原因，確認哪個行為值得修改，再用新的工作觀察修改是否有效。

例如，連續幾次交付都因英文按鈕換行而返工，可以把雙語畫面檢查放進必要驗收。若大量等待來自重跑完全無關的檢查，就研究檢查與變更的依賴關係。兩者對應不同問題；增加更多 logs，並不會自動給出相同答案。

有些決策可以直接交給程式，例如版本是否相同、檢查是否缺少、目前是否具備發布授權。另一些問題仍需判斷，例如某種版面是否符合客戶想要的視覺效果。區分這些問題，可以減少讓模型重複猜測的機會，也保留需要人工或語意評估的部分。

真正能累積的產品能力，是更準確地辨識哪一類工作可以直接完成、哪一類需要補充證據，以及補充哪個觀察最有用。這仍然需要實際結果支持，不能只靠資料量或架構圖宣稱成立。

## 用結果衡量產品，再回到架構

回到最初的疑問，兩個產品擁有相同元件並不奇怪。要判斷它們是否實際同質化，可以把同一個需求交給它們，觀察成果、失敗恢復與使用者剩餘工作。

如果換成通用 Agent 後，結果與人工投入幾乎不變，新增的產品層就還需要證明價值。如果它能穩定減少重述需求、漏查條件與反覆返工，即使底層使用相同模型，也已經形成可觀察的差異。這種差異能否持續、是否足以讓人付費，則是後續需要驗證的問題。

用英文簡短解釋這項設計，可以這樣說：

**Why can similar agent stacks produce different products?** Shared components describe available capabilities. Product value depends on whether those capabilities complete a specific job and how much work remains for the user.

**What does version-bound evidence guarantee?** It can detect a mismatch between the checked artifact and the delivered artifact. It does not prove that the checks cover every requirement or that deployment is authorized.

整個判斷可以整理成一份 Master Map：需求決定驗收條件；候選版本決定證據的適用範圍；證據缺口決定下一個觀察；通過驗收的工作與全部投入決定交付成本。共同元件是這些操作的基礎，使用者得到的成果才是比較產品的起點。
